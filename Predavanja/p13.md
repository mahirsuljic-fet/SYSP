Postoje user space threadovi i kernel threadovi.
Mi ovdje govorimo o kernel threadovima.
Kernel threadovi se mapiraju na CPU jezgro, sto nije nužno taćno za user space threadove.

### `std::lock_guard`

`std::lock_guard` je templetizirana klasa koja koristi RAII sa lock-able tipovima i koristi se za osiguravanje kritičnih sekcija.
Lock-able u ovom kontekstu znači da ima metode `lock` i `unlock`.
Najčešće se `std::lock_guard` koristi sa `std::mutex` kao template argumentom.

`std::lock_guard` se konstruiše koristeći tip sa kojim je templetiziran kao argument (npr. `std::lock_guard<std::mutex>` uzima `std::mutex` kao argument).
Prilikom konstrukcije `std::lock_guard` poziva `lock` na objektu sa kojim je kreiran.
Prilikom destrukcije poziva `unlock`.

U daljoj analizi će se pretpostavljati da govorimo o `std::lock_guard<std::mutex>`.

Ovime se stanje *(zaključanost)* mutex-a vezuje za lifetime `std::lock_guard`.

Tipično se pravi novi lokalni scope u kojem se konstruiše lock guard i time zaključa kritična sekcija, a izlazkom iz scope-a se poziva destruktor što rezultuje otključavanjem kritične sekcije.

Primjer:
``` cpp
std::mutex mtx;

void foo()
{
    // ...
    // neki proračun, mutex je otključan
    // ...

    { // početak kritične sekcije
        // koristi se automatsko zaključivanje template argumenta
        std::lock_guard lg { mtx }; // zaključavanje mutex-a
        
        // ...
        // proračun u kritičnoj sekciji
        // kojem samo jedan thread može pristupiti u datom trenutku
        // ...
    } // kraj kritične sekcije, otključavanje mutex-a

    // mutex je otključan
}
```

Mutex radi na principu sve ili ništa (jedan thread ima unikatan pristup kritičnoj sekciji).

Potencijalno nam nekada treba da više threadova pristupa istoj kritičnoj sekciji.
Glavni cilj toga je poboljšavanje performansi.

Primjer programa koji bi trebao dozvoliti više niti pristupa istim resursima je DBMS.

Prilikom dizajna multithreaded aplikacije potrebno je izabrati granularnost, šta nam je tačno kritična sekcija.
Npr. cijela baza, tabele, redovi ili čak individualne ćelije.

#### `std::unique_lock`

Postoji još jedan tip u c++ standardnoj biblioteci koji se ponaša veoma slično kao `std::lock_guard`, ali ima neke dodatne karakteristike/mogućnosti.

`std::unique_lock` je također templetizirana klasa koristi RAII da vezuje stanje mutex-a za svoj lifetime.
Međutim, ima dvije dodatne bitne karakteristike.

Prva je da se (za razliku od `std::lock_guard`) `std::unique_lock` može *"ručno"* zaključavati i otključavati koristeći metode `lock` i `unlock`.
Bitna stvar je da pozivom metoda `unlock` `std::unique_lock` gubi vlasništvo nad lock-om (mutex-om).
Zbog toga je pozivanje `unlock` nad otključanim `std::unique_lock` nedefinisano ponašanje.
Najčešće će se u tom slučaju baciti `std::system_error`, ali ne nužno (jer je u pitanju nedefinisano ponašanje).

Druga je da je `std::unique_lock` (opet za razliku od `std::lock_guard` i `std::mutex`) move-able.
To znači da je moguć transfer ownership-a `std::unique_lock`-a pri čemu `std::unique_lock` iz kojeg se vrši move ostaje u *default*/*"praznom"* stanju, tj. nema sa sobom asociran sinhronizacijski pritimiv i neće ništa raditi prilikom destrukcije sa stanovišta zaključavanja i otključavanja.


### `std::atomic`

`std::atomic` je još jedan sinhronizacijski primitiv koji nećemo koristiti.
Osigurava da neke operacije na datom tipu napravi atomskim.
Npr. `++x` nije atomski jer se (tipično) kompajlira u tri instrukcije (fetch, execute i write).

`std::atomic<int>` je specijalizacija od `std::atomic` koji ima thread safe operatore.
Ali ima probleme gdje npr. `x = x + 5` nije atomski.\*
Zbog ovakvih činjenica ih nećemo koristiti (osim eventualno u nekim veoma jednostavnim slučajevima).

\**Ovo je zato jer se `x` čita atomski, ali zatim dodavanje i upisivanje su distinktne operacije pa cijeli izraz nije atomski. `std::atomic` ima metode koji omogućavaju ovo operaciju i slične operacije da se izvode atomski, kao npr. `fetch_add`, ali zbog kompleksnosti memorijskog modela se ne preporučuje upotreba - lahko je napraviti grešku.*

Koristi se u implementacijama lock-free (lockless) struktura podataka.

Svaki\*\* lock je sistemski poziv što je skupo sa stanovista performansi, tako da lock-free strukture podataka su inherentno performantnije.

\*\**Moderni mutexi pokušavaju zaključati mutex u user space-u koristeći atomske operacije. Sistemski poziv se izvršava ako postoji konkurencija, tj. ako je mutex već zaključan.*


### `std::condition_variable`

`std::condition_variable` sinhronizicijski primitiv koji omogućava sinhronizaciju threadova koristeći neki uslov.

Moćniji je od mutex-a jer omogućava atomsko provjeravanje uslova i ne troši CPU resurse ukoliko uslov nije zadovoljen.

Efektivno, mutex se koristi za ekskluzivni pristup dijeljenom resursu, a condition variable se koristi za koordinaciju radnog toga threadova.

Metod `wait` uzima referencu na `std::unique_lock<std::mutex>`:
``` cpp
void wait( std::unique_lock<std::mutex>& lock );
```

Ono što `wait` radi je otključava `lock` (argument) i šalje thread na spavanje.
Prilikom buđenja thread će ponovo zaključati `lock` i nastaviti izvršavanje gdje je stao.

Postoji override od metoda `wait` koji se češće koristi ali interno implementira koristeći `wait` koji uzima `std::unique_lock`:
``` cpp
template< class Predicate >
void wait( std::unique_lock<std::mutex>& lock, Predicate pred );
```

Ovaj `wait` uzima predicate funkciju (npr. lambdu) koja treba da vraća `bool` (ili nešto što se može implicitno pretvoriti u `bool`).
Pozivom ovog `wait` će thread blokirati sve dok uslov dat predicate funkcijom **nije** tačan.
Efektivno, predicate funkcijom se govori uslov za nastavak izvršavanja koda.

Ovaj `wait` se implementira kao:
``` cpp
template <typename Predicate>
void wait(std::unique_lock<std::mutex>& lock, Predicate p)
{
  while (!p())
    wait(lock);
}
```
Koristi se `while` umjesto `if` zbog tzv. *spurious wakeups*.
To su buđenja thread-a usljed kernel scheduling-a.
To izaziva buđenje thread-a bez poziva `notify`, što znači da se potencijalno thread može probuditi iako uslov za nastavak nije ispunjen.

Primjer čekanja da drugi thread počne izvršavanje koristeći condition variable:
``` cpp
std::atomic<bool> b = false;
std::thread t( [&b](){ b = true; } );

std::mutex mtx;
std::condition_variable cv;

{
    std::unique_lock ul { mtx };
    cv.wait( ul, [&b](){ return b; } );
    std::cout << "Thread t je počeo izvršavanje!" << std::endl;
}

t.join();
```

Ovo je čest pattern korištenja `std::condition_variable`.
Unutar kritične sekcije se kreira `std::unique_lock` koji zaključava `std::mutex`.
Negdje u kritičnoj sekciji se poziva `wait` sa predicate funkcijom.
Ukoliko uslov nije ispunjen `std::mutex` se otključava (preko metoda `unlock` od `std::unique_lock`) i thread ide na spavanje.
Kada se thread probudi `std::mutex` se zaključava (sa `lock` od `std::unique_lock`) i provjerava se uslov.
Ukoliko uslov nije tačan proces se ponavlja.
Ukoliko uslov jest tačan thread nastavlja dalje sa zaključanim `std::mutex`-om.
Izlaskom iz scope-a gdje je definisan `std::unique_lock` se poziva njegov destruktor i `std::mutex` se otključava.

Thread koji ide na spavanje se stavlja u tzv. wait queue.
To je jednostavno red threadova koji čekaju na condition varijabli.

Bitno je napomenuti da i `std::mutex` interno ima queue thread-ova koji čekaju na mutex.
Time `std::condition_variable` efektivno ima dva thread wait queue-a, jedan od mutex-a, a drugi od same condition variable unutar kernela.

Ti threadovi se mogu probuditi koliko ih kernel schedule-a ili eksplicitno koristeći metode `notify_one` i `notify_all`.
Metod `notify_one` budi prvi thread iz wait queue-a, a `notify_all` budi sve threadove koji čekaju u wait queue-u.

Tipično se `notify_one` koristi za niti koje pišu, a `notify_all` za niti koje čitaju.

`notify_one`, `notify_all` i `wait` su efektivno wrapperi oko sistemskih poziva (uz neke dodatne stvari).

`std::condition_variable` koristi `std::unique_lock` jer `std::lock_guard` se ne može "ručno" zaključati i otključati (nema `lock` i `unlock` metode).

Konstrukcijom `std::condition_variable` se pravi condition variable na kernel strani.
Većina implementacije condition variable je zapravo unutar kernela i `std::condition_variable` se efektivno ponaša kao user space handle za kernel space condition variable.

Unutar kernela `std::condition_variable` se implementira koristeći spinlock, flag i queue.
Spinlock i flag se koristi prilikom ažuriranja stanja same condition varijable.
Queue je wait queue i predstavlja red ID-ova niti koje čekaju na condition variabli.
