### Signali

*Nastavak [predavanja 6](./p6.md).*

Signal handleri se izvršavaju u user space-u.

U `proc` sturkturu od procesa imaju tri polja koja se tiču procesiranja signala:
- vektori bita `pending`
- vektori bita `blocked`
- signal handleri (dispozicija)

Svaki bit u vektoru je zaslužen za jedan signal.

Ako je signal pending i nije blocked to znaci da treba biti procesiran.

Child proces dobija dispoziciju i `blocked` status, ali ne dobija `pending` status od parent-a prilikom `fork`-a.
Pozivom `exec` resetuje dispoziciju, tj. postavlja signal handlere na default, ali ne mijenja masku blocked i ignorisanih signala

Kernel signal procesira tako da set-uje bit u `pending` vektoru u `proc` strukturi od tog procesa.
Ako dva procesa pošalju trećem procesu jedan te isti signal u isto vrijeme, on će biti procesiran samo jednom.

Signal se procesira prilikom tranzicije iz kernel u user mode (schedule-a se proces ili povratak iz sistemskog poziva).

Da bi procesirao signal, proces mora biti u RUNNABLE stanju.
Dakle, ako je proces u WAITING stanju, ne može procesirati signal.
Kernel ***može*** (ali ne nužno mora) probuditi proces dok je WAITING stanju ako taj proces dobije signal.
Ako se signal tretira dok je proces u WAITING stanju, kernel će vratit neuspijeh kao rezultat tog sistemskog poziva. \*

\**Postoje i uninterruptible sistemski pozivi kao npr. čekanje na disk. Prilikom izvršavanja takvih sistemskih poziva signali se ne tretiraju.*

Izvršavanje handlera može biti prekinuto timer interuptom.

Korisne funkcije i tipovi vezano za signale:
- `sigset_t`    - set signala
- `sigaddset`   - dodaje signal u signal set
- `sigdelset`   - brise signal iz signal seta
- `sigismember` - projverava da li je signal dio singal seta
- `sigprocmask` - blokira ili odblokira signale iz signal set-a
' `sa_flags` - dodatke postavke za signal koje govorimo kernelu

`signal` ne postavlja blocked bit, resetuje signal handler nakon izvršavanja handlera\*\*, pa se smatra legacy API-om

\*\**Na nekim sistemima, ali ne svim.*

Moderna verzija `signal` je `sigaction`.

U Operativnim sistemima smo naučili `fork` multitasking model, naučit ćemo dodatno threading (`std::thread`) i IO multipleksiranje (`select`).

Forking model se zasniva na sistemskom pozivu `fork`.

Kada child proces terminira prelazi u ZOMBIE stanje.
Pri tome se šalje `SIGCHLD` signal parent procesu.
Parent treba da očisti njegovu memoriju.
To radi pomoću `wait` syscall-a.
Međutim on je blokirajući.
Pozivanjem `wait` unutar `SIGCHLD` handlera se dobija blokiranje unutar signal handlera što nije poželjno.
Zbog toga svaki proces koji poziva `fork` bi trebao imati signal handler koji poziva neblokirajuc' `waitpid` kako bi oslobodio memoriju child procesa.

`SIGCHLD` se šalje i na suspendiranje.
Ako to ne želimo moćemo dodati `SA_NOCLDSTOP` flag u `sa_flags`.

Korištenjem flag-a `SA_RESTART`, kada se proces probudi iz blokiranjućeg sistemskog poziva nakon sto je signal handler bio prekinut (interruptom ili slično), kernel vraća proces u `WAITING` stanje, tj. "restartuje" syscall.

Šta ako se signal handler prekine?

Moguće je da prilikom izvršavanja signal handler-a proces bude prekinut nekim interruptom.
U tom slučaju kernel sprema trenutno stanje procesora i obustavlja izvršavanje procesa.
Na dnu user stacka procesa će se nalaziti signal frame.
Prilikom povratka iz interrupt handler-a proces će nastaviti izvršavati signal handler.

Šta ako prilikom izvršavanja signal handlera dođe drugi signal?

Prekida se izvršavanje trenutnog signal handlera i pravi se novi signal frame na dnu user stacka procesa.
Proces zatim izvršava signal handler od tog drugog signala.
Ovo je podložno race condition-ima ukoliko signal handleri pristupaju istoj memoriji.
Nakon završetka drugog signal handlera proces će nastaviti izvršavati prvi signal handler i na kraju vratiti se izvršavanju koda koji je prvobitno izvršavao.

Šta se desi sa procesom kada dobije signal?

Ukoliko je proces u RUNNABLE stanju onda će kernel samo postaviti bit u pending signal vektoru.
Ukoliko je proces u RUNNNING stanju (na drugom CPU jezgru) onda će kernel poslati IPI (Inter-Processor Interrupt).
Time se proces prebacuje iz user moda u kernel mode i izvršava IPI handler.
Kernel će postaviti bit u pending signal vektoru.
Ukoliko je proces u WAITING stanju, ponašanje zavisi od sistemskog poziva zbog kojeg je proces u WAITING stanju.
Ako je sistemski poziv uninterruptible onda će kernel samo postaviti bit u pending signal vektoru.
Ako sistemski poziv nije uninterruptible onda će kernel prekinuti izvršavanje tog sistemskog poziva pri čemu sistemski poziv tipično javlja error `EINTR` u (`errno`).
Pri tome se proces prebacuje iz WAITING u RUNNABLE stanje.
Ako je korišten flag `SA_RESTART` umjesto toga će se sistemski poziv restartovati (ako je to moguće).


## Pipe i fifo

Pipe i fifo su vrsta IPC (Inter-Process Communication).
Omogućavaju komuniciranje procesa efektivno putem queue između njih.

Pipe ne postoji na fajl sistemu (ali ima fajl deskriptor) nego samo u memoriji, dok fifo postoji na fajl sistemu (poseban inode).

Pipe se koristi za komunikaciju između procesa u nasljednoj hijerarhiji (parent-child). \
Fifo se koristi za komunikaciju između proizvoljnih procesa.

Pipe i fifo efektivno imaju isto ponašanje, tako da što vrijedi za jedno tipično vrijedi za drugo.

Pipe/fifo je data struktura na kernel strani koja podržaje push i pop operacije.
Efektivno je kao queue.

Pipe ima ograničen kapacitet.
Po defaultu kernel diktira koliki je taj kapacitet, ali moguće ga je konfiturisati.
Ukoliko se pipe napuni, i neki proces pozove `write` u pipe, taj proces ide u WAITING stanje dok se ne oslobodi prostor u pipe-u.

Za kreiranje pipe-a koristi se sistemski poziv `pipe` koji "vraća" dva fajl deskriptora, jedan u koji proces treba da piše, a drugi iz kojeg proces treba da čita.
Taj pipe se kreira unutar tog procesa.
Međutim, može se uraditi `fork` pri čemu se kopiraju ti fajl deskriptori.
Nakon `fork`-a parent i child trebaju da zatvore (syscall `close`) fajl deskriptor koji neće koristiti (npr. parent zatvori za čitanje, a child zatvori za pisanje).

Bash ima operator `|` koji pravi pipe.
Uradi `fork`, napravi pipe, prepravi fajl deskriptore i izvrši `exec`.
